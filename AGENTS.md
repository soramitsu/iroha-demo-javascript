# AGENT NOTES — iroha-demo-javascript

Last updated: 2026-10-13

## Purpose

Modern Electron + Vue 3 wallet-demo that connects directly to Torii (TAIRA staging by default; Minamoto remains a selectable mainnet preset). The UI now starts with local wallet creation first, then layers wallet balances, live-backed feature surfaces, NPOS staking for XOR, SORA Parliament governance flows, transfer/receive QR flows, and explorer metrics on top. Styling uses a glassmorphic theme with animated sakura particles. All code lives under plain Vite/Electron (no Nuxt). Pinia stores persist non-secret session/theme/locale state in localStorage while wallet secrets and confidential receive keys live in the Electron secure vault.

## Key Concepts & Flows

- **Account setup (`/account`)**: Users generate recovery phrases, derive their accountId, and save the wallet locally without needing on-chain alias registration. Saved identities now require Electron `safeStorage` or the OS-backed Windows DPAPI fallback used on native Windows and WSL2; plaintext-key persistence and automatic plaintext-to-vault migration are intentionally unsupported. The same screen also restores wallets either from a pasted 12/24-word mnemonic or from an exported backup JSON file. Every backup JSON must match the exact current `iroha-demo-wallet-backup/v1` envelope and include an encrypted `iroha-demo-confidential-wallet-backup/v2` bundle so one-time receive keys and confidential shadow state are retained; mnemonic-only JSON, confidential-v1 data, duplicate keys, unknown fields, and implicit compatibility defaults are rejected. Pasting a recovery phrase remains a separate explicit restore flow. The create/restore flow no longer exposes the dormant Advanced alias-registration panel, so this screen is strictly for local wallet creation, restore, and account switching. Account setup and active-wallet header surfaces can scan a current `role=wallet` IrohaConnect QR through camera/display capture or saved-image upload. The former generated app-role pairing QR is not exposed because the wallet does not yet persist a remote-signing app session. Scanned sessions require the exact v1 relay-bound approval protocol and must open an in-app approve/reject modal with account, session, endpoint, and chain details before any approval signature. Every subsequent transaction/signing/proof request must also show a user approval modal with request details; do not auto-sign or auto-answer relay requests.
- **Network profile resolution and write safety**: `/settings` lets users override the Torii endpoint used by wallet/governance/VPN/explorer calls. Remote endpoints require HTTPS; HTTP is loopback-only. Endpoint inspection is transient and displays the configured identity beside observed chain projections and per-feature route availability; it never silently retargets the configured wallet. TAIRA staging is fixed at `https://taira.sora.org`, chain id `fc56984b-2be7-431d-840e-21514d1883f0`, network prefix `369`, and explorer `https://taira-explorer.sora.org`. Minamoto is fixed at `https://minamoto.sora.org`, chain id `00000000-0000-0000-0000-000000000000`, network prefix `753`, and XOR asset definition `6TEAJqbb8oEPmLncoNiMRbLEK6tw`. Only those exact release HTTPS origin/profile pairs can become write-authorized; arbitrary custom endpoints remain read-only even if they report a valid identity and routes. TAIRA is reset periodically, so the transaction-binding NetworkId is never pinned at build time: endpoint inspection (`electron/endpointInspector.ts`, `electron/networkIdentityDiscovery.ts`) reads it from two independent public sources on the endpoint (`GET /v1/accounts/capabilities` `network_id`/`network_prefix` and the `GET /v1/explorer/blocks/1` genesis `hash` literal, accepted as `hash:<UPPER HEX>#<CRC>` or legacy lowercase hex) and requires them to agree. The first agreeing identity for a write endpoint is pinned (trust on first use) by the main process in `userData/network-identity-pins.json`, which re-derives the identity itself before pinning; a later different identity marks the endpoint `changed` (read-only) until the user confirms it from Settings through a native dialog. A malformed pin store fails closed. Every signer (transactions, Connect, Kaigi, VPN canonical auth, governance capability binding, confidential reads) takes the pinned NetworkId; there is no compatibility pin. Endpoint-reported metadata, prefixes, account literals, and route presence alone are not identity proof. Conflicting, mismatched, changed, unpinned, or unreachable inspection blocks every ordinary network mutation before vault access, proof generation, or signing. An otherwise unverified endpoint may attempt only the bounded faucet challenge when both identity sources agree and OpenAPI advertises the faucet policy, puzzle, prepare, submit, and global-status routes. Setup/onboarding keep chain fields read-only and mirror the active session connection.
- **Torii Bridge (Electron preload)**: `window.iroha` exposes helpers wrapped around `@iroha/iroha-js` (register account, transfer asset, explorer metrics, Connect preview, NPOS staking tx builders) plus Nexus public-lane fetch endpoints. Torii/Nexus HTTP traffic uses a Node-side fetch shim from preload so the Electron window can keep normal web security enabled. Wire requests normalize account IDs onto the active-network I105 prefix (`sorau...` on Minamoto prefix `753`, `testu...` on TAIRA prefix `369`). `/v1/accounts/{account_id}/assets` accepts only the exact `{items,total,has_more,count_mode:"exact"}` envelope and exact current 11-field rows (`account_id`, `asset`, `asset_alias`, `asset_name`, `scope`, `quantity`, four nullable primary-alias fields, and `has_primary_alias:false`); legacy `asset_id`, nested/camel variants, and unknown/missing fields fail closed. Minamoto write submissions do not attach default XOR `gas_asset_id` metadata unless the endpoint advertises a gas mapping, because the public endpoint rejects an unmapped gas asset. Native install/build staging must go through the repository wrapper and verified sibling SDK root.
- **Wallet / Send / Receive**: Vue views in `src/views`. Wallet includes an endpoint-backed faucet action using the prepared-transaction flow (`electron/faucetApi.ts`): `GET /v1/accounts/faucet/policy` (bound to the attested NetworkId; supplies issuer, asset and amount), `GET /v1/accounts/faucet/puzzle` (`scrypt-leading-zero-bits-v1`, challenge domain `iroha:accounts:faucet:pow:v1`, solved asynchronously in preload), `POST /v1/accounts/faucet/prepare` with an `iroha.prepared-operation.binding.v1` whose `semantic_hash_hex` is the domain-separated compact-Norito claim hash, then the returned `iroha.prepared-transaction.v1` envelope posted verbatim to `POST /v1/accounts/faucet` (idempotent re-post), and success only after a confirmed global pipeline status of `Applied` resolved from state. Iroha produces no empty blocks, so there is no block-height-advance precondition; surface the live Torii error rather than implying a guaranteed claim. Minamoto mainnet must never expose or use a faucet, so wallet-side faucet claims must be blocked for the public Minamoto endpoint even if a route appears. Faucet policy and puzzle metadata must match the endpoint's attested NetworkId and network prefix `369`; a mismatch is a deployment error, not something the wallet should normalize around. The wallet does not locally block repeat faucet claims just because the account already has XOR. Faucet proofs are solved against the canonical active-network I105 account literal, even if the UI is showing a differently normalized variant of the same account. During faucet claims the wallet shows a non-blocking status overlay with live bridge-reported phases (puzzle fetch, beacon-seed wait, PoW solve, prepare/submit, Applied wait, wallet refresh) and, after submit succeeds, polls account balances for a short bounded window before falling back to a “still indexing” message. Local-only wallets surface a note that balances may stay empty until the account is live on-chain, and a successful faucet claim clears the local-only marker. A fresh claim stores the exact funded `asset_definition_id` for later reads. The Wallet private-balance panel is read-only: it recovers recognized confidential notes and marks incomplete scans as inexact, but this release exposes no shield, confidential-transfer, or unshield mutation. Receive emits only `iroha-confidential-payment-address/v3`: the QR omits plaintext account, asset, and amount; carries a one-time receive key persisted in the secure vault; and exposes the same material as a copyable `iroha:confidential:v3:` address for independently compatible senders. Send exposes one transparent-transfer form, resolves account aliases to the active-network I105 literal, and never scans, parses, or submits private payment addresses. The retained camera/image QR scanners belong to Receive-independent wallet/connect flows and ignore transient frame-decode misses (`NotFoundException`, `ChecksumException`, `FormatException`).
- **Kaigi (`/kaigi`)**: Browser-native 1:1 audio/video calls. Live wallets use transparent on-chain `CreateKaigi` / `JoinKaigi` / `EndKaigi` instructions only; host and participant account IDs are therefore visible in the Torii call and signal projections. The canonical `iroha://kaigi/join?call=...&secret=...` link (or equivalent hash route) contains only an exact qualified call ID and a 24-byte unpadded-base64url invite secret. SDP remains encrypted under that invite/key exchange while Torii carries the encrypted offer and answer metadata. Private on-chain calls, proof-backed Kaigi artifacts, redacted Torii response shapes, legacy `invite=` links, raw invite tokens, duplicate/unknown parameters, and links carrying SDP, ICE, or wallet identities are unsupported. Local-only wallets may use the Advanced raw-packet flow, which remains in memory and never becomes an on-chain fallback for a live wallet. Browser media transport remains self-contained inside this Electron app. The screen exposes camera/microphone selectors, prefers built-in/FaceTime cameras over virtual devices, and treats a live camera track with no rendered frames as a recoverable setup failure. Electron media permission handling must check macOS `systemPreferences.askForMediaAccess` before granting renderer media permission.
- **VPN (`/vpn`)**: Signed-in users can open a Sora VPN control page that talks to Torii VPN profile/session endpoints through the Electron preload bridge. Renderer state in `src/stores/vpn.ts` is transient. Electron main owns the current-run VPN runtime state in `electron/vpnRuntime.ts`, reconciles the local controller against live remote Torii session state, exposes live canonical receipt history, and surfaces repair/orphaned-session flows. Legacy global active-session and receipt files are quarantined without migration; private keys, helper tickets, active sessions, and receipt caches are never persisted by the wallet. On macOS the local path is now split across a Swift `sora-vpn-controller` manager app, its nested PacketTunnel system extension, and a bundled Rust `sora-vpn-packet-engine` app that the provider uses for relay transport; the helper app persists its packet-tunnel bundle ID, app-group ID, and manager description in `Info.plist`, and local bundle/app-group overrides are available through `SORANET_VPN_HELPER_BUNDLE_ID`, `SORANET_VPN_PACKET_TUNNEL_BUNDLE_ID`, `SORANET_VPN_APP_GROUP_ID`, and `SORANET_VPN_MANAGER_DESCRIPTION` during `npm run build:vpn:macos-controller`. The renderer never configures routes or DNS directly.
- **SoraCloud (`/soracloud`)**: Signed-in users get a live SoraCloud console backed only by Torii bridge reads. The page checks `GET /v1/soracloud/status`, distinguishes endpoint-unavailable from an empty live service list, and can inspect the exact shared-lease projection at `GET /v1/soracloud/hf/lease/status` using a fully qualified repo, full 40-character lowercase commit, storage class, lease term, and optional canonical I105 account. The renderer rejects unknown/legacy fields, invalid cross-links, noncanonical hashes/accounts/assets/quantities, unbounded arrays, and non-HTTPS public URLs. Torii advertises `POST /v1/soracloud/hf/lease/join`, but this desktop release exposes no callable join or deploy mutation: the current JavaScript/native SDK does not export the exact canonical Norito encoder/signer for the typed eight-field provenance tuple. The UI states that limitation and keeps joining disabled instead of copying the codec or signing a JSON descriptor. Renderer state lives in `src/stores/soracloud.ts`, is not persisted to localStorage, and must never store API tokens, private keys, deployments, tickets, or generated credentials.
- **SCCP (runtime disabled)**: The first desktop release must not register an /sccp route, navigation item, preload bridge method, WalletConnect runtime configuration, foreign-chain RPC wrapper, proof builder, or SCCP submission path. The current sibling SDK does not expose the exact governed first-release implementation, so archived-chain descriptors, legacy relabeling, copied SDK logic, local/manifest proof fallbacks, and permissive response adapters must remain unreachable. SCCP source, tests, and operator scripts may remain only as dormant artifacts that are not imported or bundled by the renderer or preload runtime. Re-enable the product surface only after the current SDK provides an independently reviewed exact typed-registry taira_sol_xor implementation backed by route-scoped governed SORA outbound material.
- **Solana SCCP (`taira_sol_xor`)**: The first-release Solana-testnet route has exactly three distinct Loader-v3 programs: a destination bridge, a source bridge, and a native BN254 Groth16 verifier. Production artifacts must be built as exact SBPF V3 (`e_flags = 3`), deployed under fresh program IDs, and finalized with one atomic three-instruction `SetAuthority(None)` transaction before creating the classic nine-decimal SPL mint, `SCCPMAT1` verifier material, or deterministic route-state PDAs. Loader-v3 immutability is identified by the ProgramData authority option tag at byte 12 being zero; bytes 13..45 are residual metadata and must not be required to be zero. Public truth comes only from the typed TAIRA SCCP registry after separate Parliament registration and activation enactments; legacy manifest aliases, route-manager publication, mutable/four-role deployments, opaque server-side proof generation, SBPF V0/V1/V2, and account-mention-only evidence fail closed. TAIRA-origin preparation fetches exact governed IVM bytes and policy from `/v1/sccp/routes/{source_profile}/{route_id}/{asset_key}/{revision}/sora-outbound-material`; neither manifests nor renderer parameters may supply fallback bytecode, VK, gas, or settlement aliases. Browser destination/source provers must remain blocked until separately reviewed real packages and governed material are installed.
- **Solana SCCP live media**: The successful bidirectional MP4 must be derived from an independently hash-pinned real screen capture of the completed transfer flow. The capture must be duration-bounded, contain changing visible frames and non-silent audio, and the final H.264/AAC MP4 must embed the exact explanatory VTT. A synthesized solid-color/silent stream is diagnostic-only and can never satisfy production completion.
- **Offline payments (runtime disabled)**: The first desktop release does not register an `/offline` route or navigation item. The dormant prototype uses locally mutable balances and hash-only payment receipts, so it cannot authenticate a sender, prevent forged value, or provide rollback-resistant state. Keep its source unimported and unbundled until an exact allowance-backed protocol supplies sender signatures, recipient verification, replay protection, and durable anti-rollback storage; do not add compatibility parsing for prototype payloads.
- **Staking (`/staking`)**: Dataspace-first validator nomination flow for public-lane NPOS. Lanes are discovered from `/v1/nexus/lifecycle`; optional Sumeragi telemetry supplements that result without becoming a page-wide prerequisite. Validator, stake, reward, policy, asset, and lane reads use the first-release `/v1/nexus/public-lanes/...` contract and fail independently, so an unavailable lane or operator-only configuration does not blank other live data. Missing unbonding delay disables only new unbond scheduling. Bond, unbond, reward, and validator-registration mutations require both a write-authorized endpoint inspection and advertised staking operations; reads remain available in read-only mode. Stake/reward actions submit staking instructions via `buildTransaction`, and the operator panel registers the active wallet through a signed `RegisterPublicLaneValidator` transaction.
- **Governance (`/governance`)**: Taira-only SORA Parliament workspace gated by both a write-authorized endpoint inspection and an exact, fail-closed `/v1/gov/capabilities` response for chain `fc56984b-2be7-431d-840e-21514d1883f0`, prefix `369`, ABI `1`, and data model `4`. Citizenship is a separately loaded `citizen | not-citizen | unavailable` result; transport and decoding failures never render as “not a citizen,” and capability failures do not hide a valid citizenship result. Citizen count, current council, unlock statistics, validation-fee policy state, and typed validation-fee list/detail reads have independent loading/error paths. The exact capability contract describes ten timed-OVN Parliament bodies, but this wallet exposes no ballot, ceremony/transition, or enactment control; the related advertised routes remain uncallable server capabilities. Only the exact validation-fee payout-lifecycle and policy proposal kinds are writable; lifecycle is composed first and the policy must bind its certificate-enacted lifecycle payload with a 120,960-block activation delay. Unknown proposal kinds are inspect-only. Governance writes have two explicit approvals: **Decode and quote** may resolve the OS-vault key only to authenticate the exact Core draft and fee-quote requests, while **Sign and commit** revalidates capabilities, account, and signing algorithm before resolving the key again and signing the reviewed payload. Renderer and HTTP fields never carry a governance private key. There is no Electron manual finalize, PLAIN/ZK ballot, generic sponsorship, historical signer, signed-policy fallback, governance keyset, detached-signature, or browser proof-SDK path. Validation-fee state requires the exact generated `{enabled, ledgerBinding, expected}` config plus concurrent Core `/v1/validation-fee/policy` and `/v1/validation-fee/status` reads; projections must match after canonical JSON normalization and rollback/equivocation is rejected. Packaged launches load the exact config and Core URL from the strict `sora.wallet.governance-runtime.v1` manifest at `app.getPath("userData")/governance-runtime.json`; a complete environment pair may override it, but partial environment/file mixing is rejected. Integrity checkpoints live under `governance-integrity-v1` through the provenance-verified native private-file boundary.
- **Subscriptions (`/subscriptions`)**: The subscription hub is now backed by live Torii subscription endpoints instead of local sample data. It reads `/v1/subscriptions?owned_by=...` and `/v1/subscriptions/plans` through preload's Node-side fetch bridge, surfaces empty/error states from the active endpoint directly, and creates/actions real subscription NFTs with stored wallet secrets via `POST /v1/subscriptions` plus pause/resume/cancel/keep/charge-now endpoints. The Pinia store no longer persists or seeds subscription records in localStorage; old `iroha-demo:subscriptions` data is discarded on hydrate.
- **Localization (`locale`)**: App text routes through `useAppI18n` with persisted locale in `useLocaleStore` (`iroha-demo:locale`). Supported locales now cover `en-US`, `ar-SA`, `az-AZ`, `ca-ES`, `cs-CZ`, `de-DE`, `es-ES`, `fa-IR`, `fi-FI`, `fr-FR`, `he-IL`, `hi-IN`, `hu-HU`, `id-ID`, `it-IT`, `ja-JP`, `ko-KR`, `ms-MY`, `nb-NO`, `nl-NL`, `pl-PL`, `pt-PT`, `ru-RU`, `sr-RS`, `sl-SI`, `tr-TR`, `uk-UA`, `ur-PK`, `vi-VN`, `zh-CN`, and `zh-TW` with English fallback for missing keys. Auto-generated locale tables live in `src/i18n/*Auto.ts`; targeted manual overrides for governance/bonding, onboarding, and high-visibility app chrome copy (Arabic/Persian/Hebrew/Urdu) live in `src/i18n/messages.ts`. `detectPreferredLocale()` includes prefix fallbacks for the full locale set (including `iw` -> `he-IL`, `in` -> `id-ID`, `zh-hant` -> `zh-TW`, and `ur` -> `ur-PK`). Locale direction is tracked per locale (`LOCALE_DIRECTIONS`) and applied to `<html dir>` for RTL languages (`ar-SA`, `fa-IR`, `he-IL`, `ur-PK`). RTL shell styling now mirrors app structure (`.app-shell` row reversal, mirrored sidebar/card accents, caret inversion) and uses `unicode-bidi: plaintext` on mixed technical-value surfaces to stabilize ID/URL rendering in RTL UIs. Subscription amount formatting accepts locale-aware number formatting callbacks (wired from `useAppI18n().n` in `SubscriptionHubView`). `tests/i18n.spec.ts` guards against missing non-English keys (including route/nav metadata + runtime subscription-format keys) and non-technical hardcoded placeholders in Vue templates.
- **Theme & Flair**: `useThemeStore` toggles light/dark by applying `data-theme` on `<html>`. Animated sakura petals (`SakuraScene.vue`) sit behind everything (canvas z-index 0) and read CSS `--parallax-x/y` to drift + “stick” to side walls. Ensure new overlays respect pointer-events so they don’t block the sidebar.

## Tooling & Commands

- **Dev**: `npm run dev` (electron-vite). Ensure `ELECTRON_RENDERER_URL` is set automatically by electron-vite.
- **VPN controller builds**: `npm run build:vpn:controllers`, `npm run build:vpn:macos-controller`, and `npm run build:vpn:linux-controller` stage the bundled local VPN runtime artifacts used by Electron. The macOS build assembles one self-contained `SoraVpnController.app` with `SoraVpnPacketEngine.app` under `Contents/Resources/vpn` and exactly one bundle-ID-matched system extension under `Contents/Library/SystemExtensions`. When `APPLE_DEVELOPMENT_TEAM` is set, the macOS build attempts real Apple provisioning/signing for the helper app and PacketTunnel extension and hard-fails if Apple strips the required VPN entitlements; optional local bundle/app-group overrides come from `SORANET_VPN_HELPER_BUNDLE_ID`, `SORANET_VPN_PACKET_TUNNEL_BUNDLE_ID`, `SORANET_VPN_APP_GROUP_ID`, and `SORANET_VPN_MANAGER_DESCRIPTION`.
- **Packaging**: `npm run dist`, `npm run dist:mac`, `npm run dist:win`, and `npm run dist:linux` first require the reviewed Iroha SDK release-source gate, then run electron-vite, stage platform VPN controller artifacts where available, and package artifacts with `electron-builder`. There is no ungated development-installer command; use `npm run build` for local development output. Packaged runtime contains only the canonical `dist/native` binding and manifest; the full `@iroha/iroha-js` source package is excluded. macOS packaging embeds only the validated self-contained `SoraVpnController.app` under `Contents/Helpers`; Linux packaging copies only `sora-vpn-controller`. Broad staging-directory copies and legacy `.bundle`/`.appex` alternatives are forbidden. The Electron host app keeps plain Electron entitlements; restricted NetworkExtension/App Group entitlements belong only on the nested helper path, which Electron's general signer must ignore so it preserves its separate signatures. The Developer-ID `.systemextension` path requires exact `packet-tunnel-provider-systemextension`; the app-extension-only value is unsupported. Release builds require exact platform-signing identities and trusted timestamps, reject debugger-enabled final signatures, verify final nested signatures and entitlements, and require a stapled macOS notarization ticket before upload.
- **Release publishing**: `.github/workflows/release.yml` builds draft GitHub releases from existing `v*` tags after checking out this repo beside `hyperledger-iroha/iroha` for the local `@iroha/iroha-js` dependency. It requires a public-only reviewed OpenPGP key from `IROHA_RELEASE_SIGNER_PUBLIC_KEY_BASE64`, imports it into an isolated keyring, and uses the same `install:release` / `verify:iroha-sdk` corridor as every installer-producing command so Vite and native staging select one authenticated physical SDK package. It publishes macOS x64/arm64 DMG+ZIP, Windows x64 NSIS+ZIP, Linux x64 AppImage+DEB+RPM artifacts, and `SHA256SUMS.txt`. The workflow keeps the current SDK source unmodified and packages no historical signer/proof compatibility binding. macOS release jobs require Developer ID signing/notarization secrets plus Apple-granted NetworkExtension/App Group entitlements for the VPN helper path; Windows jobs require an Authenticode signing certificate and must sign and post-sign verify the packaged `.node` addon as well as the executable. Release operator notes and v2.0.1 validation-fee runtime inputs live in `RELEASE.md`.
- **Tests**: `npm test` (Vitest + jsdom). Current suites cover session, theme, and transaction helper logic.
- **Lint/Typecheck**: `npm run lint`, `npm run typecheck` (renderer + Electron), plus `npm run typecheck:renderer` / `npm run typecheck:electron`.
- **UI E2E**: `npm run e2e:ui` runs a deterministic Playwright smoke pass against the renderer with synthetic media, including Kaigi device selection, camera fallback, meeting-link creation, and join summary checks. Set `E2E_REAL_MEDIA=1 E2E_BROWSER_CHANNEL=chrome npm run e2e:ui` only for an explicit real-device camera pass; it uses real browser media and expects actual decoded video frames, so OS privacy denial, virtual camera dead feeds, or Chromium device-service failures should fail the run.
- **Live verification bundles**: `npm run verify:live` (base verify + strict live TAIRA E2E for the active first-release surfaces; the wallet app defaults to TAIRA staging).
- **TAIRA contract checks**: `npm run verify:live:taira-reads` is the opt-in GET-only diagnostic check for the deployed endpoint. It does not enable legacy routes or response adapters. `npm run verify:live:taira-v2` is the GET-only release gate and requires the exact official identity plus the required first-release write-route inventory. Run the mutating `npm run verify:live` only after that gate passes.
- **Verification bundles**: `npm run verify` (lint + typecheck + unit tests).
- **Live VPN surface check**: `npm run verify:live:vpn-surface` verifies that the deployed Torii node is healthy, serves `/v1/mcp`, publishes the VPN paths in `/openapi.json`, exposes the `iroha.vpn.*` MCP aliases, and serves `/v1/vpn/profile` before attempting VPN-focused live bring-up; it defaults to Minamoto.
- **Live E2E**: `npm run e2e:live` (defaults to TAIRA Torii + chain ID, strict reachability preflight, and a fresh faucet-funded local wallet unless `E2E_FUNDED_PRIVATE_KEY_HEX` is set; set `E2E_REUSE_FUNDED_CACHE=1` only when intentionally reusing `output/e2e/live-funded-wallet.json`). It validates Explore metrics/QR and route-smoke checks for Setup/Wallet/Staking/Parliament/Subscriptions/SoraCloud/Send/Receive. `E2E_ASSET_DEFINITION_ID` is optional because the harness can derive it from the faucet response or funded-wallet holdings. The app does not require UAID onboarding to create a wallet.

## Gotchas

- Always keep UI layers above the sakura canvas (set container `z-index` if adding new wrappers). Canvas must stay `pointer-events: none`.
- Account guard will redirect to `/account` if `session.hasAccount` is false. This is now a local-wallet guard, not proof that the account exists on-chain. When testing other routes, seed `session.accounts[]` with an active account containing `accountId` and `hasStoredSecret: true`; `privateKeyHex` alone no longer counts as a saved wallet.
- Setup/account setup keep chain ID and network prefix read-only. Torii endpoint and chain metadata changes belong in `/settings`, which persists the checked endpoint metadata and re-derives stored account literals when the network prefix changes.
- New live surfaces target one first-release contract. Do not add alternate legacy routes, response-shape adapters, URL-only cache migrations, or silent endpoint-identity fallbacks.
- Current IrohaConnect wallet-role QR payloads require exact `v=1`, `token`, and separate `relay` parameters. Approval uses a fresh in-memory X25519 key, the two-stage SDK HKDF, and an Ed25519 signature over the relay-bound `iroha-connect|approve|v1` preimage. Enforce session ID and direction on every frame, with independent monotonic counters for peer app frames and relay `server_event` frames. Approval permissions/proof remain `None`, but the wallet must retain the Open permission manifest internally: raw signing requires exact `sign_raw` plus exact domain membership in `resources`, transaction signing requires exact `sign_transaction` (a session may grant both), and every allowed signing request still requires its own modal plus the native dialog. `SignRequestTx` carries the unsigned payload bytes from the SDK's `buildTransactionPayload`; preload (`electron/connectTransactionReview.ts`) validates them with the SDK codec, requires the payload authority to be the paired account and its NetworkId to be the session's pinned NetworkId, decodes every instruction with the native Norito decoder into a review (transfers, mint/burn, `Grant` of `CanExecuteSettlement`, `Settlement::Atomic` movements and escrow legs, escrow and repo instructions, unknown ones by wire ID plus JSON, undecodable ones by wire ID with a warning), and after approval signs only `HashOf<TransactionPayload>` (BLAKE2b-256, low bit set) re-derived from the exact bytes. Unreviewable payloads are answered with `INVALID_TRANSACTION`. `SignRequestRaw` keeps signing the exact domain-tagged message bytes. `iroha://connect?…&role=wallet&token=&relay=` links from the OS (macOS `open-url`, launch/second-instance argv) are validated in main with `parseIrohaConnectUri`, held until the header Connect surface takes them through preload, and then follow the same approval modal as a scanned QR.
- Route header titles/subtitles now use route meta keys (`titleKey`, `subtitleKey`) and are translated in `App.vue`.
- SoraCloud is live-data-only. Keep `/soracloud` wired only to `window.iroha.getSoraCloudStatus` and `window.iroha.getSoraCloudHfSharedLeaseStatus`; do not add sample deployments, fake pricing, tickets, API tokens, private keys, or real deployment credentials to localStorage/Pinia. If the active Torii endpoint returns 404/405/501 for `/v1/soracloud/status`, the UI must show endpoint unavailable rather than zero live services. Keep shared-lease joining visibly disabled until the current SDK exports the exact typed canonical Norito provenance encoder/signer; do not add an obsolete deploy route, JSON-signing substitute, or copied codec.
- Renderer code must import browser-safe SDK subpaths and must not import the `@iroha/iroha-js` package root from `src/`, because the root can pull Node-only modules into the Vite browser bundle. Governance uses renderer-owned DTOs and delegates native decoding, fee quoting, and signing to preload.
- Governance proposal IDs are canonical 32-byte hex. Unsupported proposal kinds are inspect-only, ZK ballots have no plain fallback, and validation-fee state must stay unavailable unless the exact generated runtime config matches identical raw-policy and status projections from CBSI Core.
- The packaged governance runtime manifest is re-read for every validation-fee policy refresh. Provision `governance-runtime.json` atomically under Electron `userData`; never cache a previously valid manifest after it is deleted or becomes invalid. `GOVERNANCE_VALIDATION_FEE_CONFIG_JSON` and `CBSI_CORE_API_BASE_URL` are a strict all-or-nothing override and must never be combined with file fields.
- VPN actions require both an active local wallet account and the bundled platform-specific local artifacts. On macOS that means the validated `SoraVpnController.app` with its nested packet-engine app and PacketTunnel system extension; on Linux it remains the bundled `sora-vpn-controller` helper.

The build now stops with an explicit entitlement error if Xcode strips those keys instead of silently staging a broken helper.
- VPN runtime state is current-run only. On startup, `electron/vpnRuntime.ts` deletes the legacy global `active-session.json` and `receipts.json` files without migration; live Torii receipt reads and platform-controller reconciliation are authoritative. Keep receipt memory scoped to the exact endpoint/chain/prefix/account context, hide active-session details after a context switch, and never persist wallet private keys, helper tickets, active sessions, receipt caches, or private controller secrets in Electron `userData`, Pinia, or localStorage. Controller repair is local-only and must remain available without endpoint identity, VPN profile, Torii, or vault access.
- macOS PacketTunnel controller/extension state defaults to the shared app-group container (`group.org.sora.wallet.demo.vpn`) when entitlements are present, with `SORANET_VPN_STATE_FILE` as an explicit override for local debugging.
- Onboarding/persistence accepts only the current session envelope and canonical I105 account IDs in `accountId`. Retired snapshot shapes are deleted or rejected without migration; saved secrets resolve only from the secure vault and never from renderer state.
- WSL2 wallet saves can use Windows DPAPI through `powershell.exe` when Electron `safeStorage` cannot reach GNOME Keyring/libsecret. This still writes only DPAPI-encrypted vault entries and should not be replaced with a plaintext Linux fallback.
- Live onboarding E2E reuses one deterministic onboarding account (`E2E_ONBOARDING_PRIVATE_KEY_HEX`) so repeated runs do not keep creating TAIRA onboarding records.

- Kaigi invite links carry only `call` + `secret`; do not reintroduce SDP, ICE candidates, or wallet IDs into shareable links. Live on-chain calls are transparent and must not accept private-proof or redacted-response variants.
- Kaigi media readiness must be based on rendered local preview frames (`videoWidth` / `videoHeight`), not just a live `MediaStreamTrack`. Some macOS setups expose a live track with zero frames when the OS permission is denied or a virtual camera is selected but unplugged.
- The private-balance panel is a read-only recovery view. Missing encrypted note metadata makes the displayed total inexact, and the UI must not describe it as spendable. Receive creates exact `v3` one-time addresses for compatible external senders; this app's Send surface remains transparent-only and must not parse private-address payloads.
